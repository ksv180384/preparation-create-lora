# Пошаговая реализация

Точка входа: [PLAN.md](../../PLAN.md). Фактический прогресс: [PROGRESS.md](PROGRESS.md).
Обозначения спецификаций: D — DATA_MODEL.md, C — CONTRACTS.md, P/U — PIPELINE_AND_UI.md.

## Правила выполнения этапа

- Не начинать этап, пока его зависимости не реализованы.
- Прочитать указанные разделы и существующий код. Сначала определить границы небольшой задачи и ожидаемое поведение.
- Не копировать весь план в комментарии к коду. Имена и контракты брать из спецификаций.
- До реализации взаимодействия добавить request/response examples в contracts/. После изменения контракта обновить потребителей.
- Проверки в этом документе — требования к будущей реализации. Сейчас они не считаются выполненными.
- Предпочитать проверки наблюдаемого поведения: файл сохранён, конфликт отклонён, UI восстановлен. Не создавать тесты, которые только повторяют код.
- Для каждого законченного этапа сохранить команды проверок и результат, включая ограничения реальной среды.
- Незаконченная проверка означает partial/blocked для соответствующей части, но не запрещает независимую работу внутри разрешённого объёма.
- «Готово» требует работающего сценария через реальный API; заглушка LM Studio полезна для ошибок, но не подтверждает реальный vision.
- В каркасе определить стандартные команды проверок: Laravel — php artisan test; Python — python -m pytest; Vue/Node — npm run typecheck и npm run test:ci (однократный запуск без watch). Запускать их в контейнерах с dev-зависимостями и сохранять точные Compose-команды в README. Для инфраструктуры использовать docker compose config --quiet и реальные HTTP-проверки. Не выдавать эти команды за уже выполненные.
- После изменения данных/файлов проверять обратную совместимость сохранённых ревизий.
