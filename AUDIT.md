# Аудит плана студии подготовки LoRA-датасетов

Дата: 23 октября 2026 года.

Основание: обсуждение в чате и текущий PLAN.md. Рассмотрены архитектура, подготовка данных, интерфейс, надёжность и порядок разработки. Технические утверждения сверены с официальной документацией и исходниками проектов. Запуск приложения, измерения на RTX 4070 Ti Super и проверка установленной LM Studio не выполнялись: это аудит проекта до реализации. PLAN.md в рамках аудита не изменён.

## Общая оценка

Выбранный стек подходит. Vue 3, Laravel, Python, PostgreSQL и Node/Fastify/Socket.IO можно сохранить. Docker Compose в WSL2 с LM Studio на Windows — разумное размещение. Главные риски связаны с правилами работы с изображениями, ревизиями и параллельными изменениями.

В плане уже удачно предусмотрены сохранение исходников, независимые профили экспорта, ручная проверка, разнообразие отбора, виртуальная галерея, история подписей, fingerprints этапов, outbox, аренда задач и восстановление состояния через API. Ниже уточняется, чего недостаточно для реализации этих обещаний.

Приоритет P1 означает, что правило нужно определить до реализации соответствующего сценария: иначе возможны потеря ручных изменений, неверный датасет или конфликт файлов. P2 — важная доработка качества и удобства. Это риски спецификации, а не подтверждённые ошибки готового приложения.

## Выбор технологий

| Решение | Оценка и границы ответственности |
| --- | --- |
| Vue 3 + TypeScript | Подходит для галереи, редактора подписей, массовых операций и фонового прогресса. |
| Laravel | Оставить владельцем бизнес-логики, схемы БД, авторизации, ревизий, очереди обработки и публикации событий. |
| Python | Подходит для изображений, CV и запросов к LM Studio. Для исходящего worker отдельный FastAPI-сервер не нужен без конкретной необходимости. |
| PostgreSQL | Подходит для связанных сущностей, ревизий, очередей и outbox. Сотни изображений сами по себе не требуют PostgreSQL; здесь выбор оправдан общей моделью приложения и согласованным стеком. |
| Node/Fastify/Socket.IO | Обоснован принятым требованием. Сервис принимает внутренние события, проверяет подписки и доставляет обновления; бизнес-логика остаётся в Laravel. |
| Docker Compose + WSL2 | Удобная повторяемая среда. Нужны описанные точки монтирования, UID/GID, запуск, обновление и восстановление. |
| LM Studio на Windows | Оставить внешней интеграцией. Проверка доступности выполняется из Python-контейнера. |
| Отсутствие Redis/Kafka | Для первого локального варианта разумно. Laravel-очередь публикации и Python ProcessingJob должны иметь явно разные роли; обе могут храниться в PostgreSQL. |

Один backend-запрос или изменение состояния не должны ждать доставки всем браузерам. Подтверждение Node означает приём события шлюзом. Socket.IO по умолчанию не обеспечивает повторную доставку всех пропущенных серверных событий, поэтому snapshot из Laravel остаётся обязательным. [Socket.IO: гарантии доставки](https://socket.io/docs/v4/delivery-guarantees/).

## Замечания к плану

### P1-01. Уточнить модель редактируемого набора и опубликованного экспорта

Места: PLAN.md, строки 108–110, 144–157, 161–163.

Пользователь хочет менять подписи и удалять изображения в созданных папках. План описывает просмотр экспортов и общую историю подписей, но не определяет, меняется ли при таком действии исходная коллекция, готовая папка или новая версия.

Предлагаемая модель: коллекция исходников → редактируемый набор → опубликованная ревизия → экспорт в папку/ZIP. Набор хранит выбранные изображения, преобразования и подписи для своего профиля. Опубликованная ревизия фиксирует состав и хеши; кнопка «Редактировать» открывает новый черновик с понятной связью с предыдущей версией. Это сохраняет возможность редактирования подготовленных изображений и воспроизводимость уже использованного датасета.

Разделить состояние анализа, решение пользователя, включение в конкретный набор и принадлежность к экспорту. Изображение может одновременно быть проверенным, включённым в два набора и экспортированным; одного взаимоисключающего статуса для этого недостаточно.

### P1-02. Защитить ручные подписи от фоновой перезаписи

Места: PLAN.md, строки 107–108, 146, 161–163.

Наличие CaptionRevision не определяет правила конфликтов. Пример: пользователь исправляет описание, пока LM Studio ещё генерирует предыдущую версию; пришедший ответ может затереть правку.

Добавить источник подписи (импорт / модель / ручная), блокировку ручной подписи, номер ревизии и проверку ожидаемой версии при сохранении. Фоновый результат, основанный на старой версии, сохраняется как предложение. Для перегенерации нужны варианты «только отсутствующие», «только автоматические», «заменить выбранные после просмотра». Перед массовым изменением показывать diff и количество затронутых файлов; предусмотреть откат.

При экспорте дождаться сохранения текущего редактирования и зафиксировать номера ревизий подписей. Сохранённый экспорт не должен меняться при последующих правках коллекции.

### P1-03. Гарантия сохранения персонажа должна учитывать преобразования тренера

Места: PLAN.md, строки 78–82, 150–157.

Сохранение пропорций в приложении само по себе не гарантирует, что тренер не обрежет изображение при приведении к bucket. В sd-scripts обработка при кешировании вызывает trim_and_resize_if_required с параметрами bucket и crop. [Исходники sd-scripts](https://github.com/kohya-ss/sd-scripts/blob/main/library/caching.py).

Для каждого проверенного профиля определить, где выполняются resize/crop и какие преобразования остаются тренеру. Предпросмотр «Как увидит тренер» должен воспроизводить эту геометрию. При несовместимом соотношении сторон предложить ручной crop, подходящий bucket либо исключение; padding разрешать осознанно, поскольку он добавляет в обучающие данные поля. Автоматическое дорисовывание тела не использовать как обычное исправление.

Подпись должна соответствовать итоговому кадру. Если crop изменился, автоматическая подпись становится устаревшей; ручная получает отметку «проверить соответствие». В fingerprint подписи включить фактический вход изображения для captioning.

### P1-04. Добавить проверку принадлежности нужному персонажу

Места: PLAN.md, строки 118–128.

Количество людей и разнообразие кадров не определяют, что на всех 500 изображениях один нужный персонаж. Сейчас план упоминает пересечения коллекций, но не задаёт проверку идентичности внутри коллекции.

Дать выбрать несколько эталонов персонажа с разными ракурсами. Сходство использовать для очереди подозрительных кадров с просмотром эталона рядом. Для фотографий и рисунков нужны разные проверенные подходы; отсутствие видимого лица не должно автоматически исключать кадр. Автоматическое сходство остаётся подсказкой для пользователя.

Правило «два и более человека — исключить» сохранить, но определить пограничные случаи: отражение, постер с человеком, коллаж, маленькая фигура на фоне, крупный портрет с нераспознанным телом. Отсутствие детекций не доказывает отсутствие человека. Показывать рамки детектора, причину решения и ручную проверку. На размеченной выборке оценивать отдельно пропущенные многолюдные кадры и ошибочно исключённые одиночные.

### P1-05. Сделать общий планировщик ресурсов для всех коллекций

Места: PLAN.md, строки 39, 63–65, 75–78, 189.

«Один активный запрос» нужно определить на всё приложение: несколько коллекций, пробная генерация и проверка vision-модели не должны создавать независимые GPU-очереди с одновременными запросами.

Предусмотреть общий слот LM Studio, отдельную ограниченную очередь CPU-этапов, приоритет короткой проверки и справедливое продвижение коллекций. При недоступности LM Studio останавливать зависимые этапы описания; импорт, просмотр, хеширование и подходящие CPU-этапы могут продолжаться.

Задать состояния задачи и разрешённые переходы: в очереди, выполняется, ждёт ресурс, приостановлена, отменяется, отменена, завершена с ошибками, завершена. Пауза и отмена проверяются на границах этапов. Поздний ответ отменённой попытки не должен переводить задачу обратно в успешную. Если внешняя модель не подтверждает отмену вычисления, UI должен честно показывать это ограничение.

Приложение может координировать собственные запросы; занятость видеокарты другими Windows-программами оно полностью не контролирует.

### P1-06. Аренда задачи не защищает общий каталог сама по себе

Место: PLAN.md, строка 39.

Текущий план обещает, что устаревший worker не запишет результат. Laravel может отклонить его API-запрос, но Python имеет прямой доступ к общему тому. После потери аренды старый процесс всё ещё способен перезаписать файл по общему итоговому имени.

Каждая попытка должна писать в собственный уникальный путь. Публикация результата выполняется через Laravel после проверки lease_token, состояния задачи и актуальной версии входа. Принятые производные файлы — неизменяемые; в БД фиксируется ссылка на выбранный артефакт. Общий изменяемый путь не должен быть целью записи разных попыток.

Нужны также отдельный heartbeat во время долгого inference, восстановление при потере ответа complete и уборка осиротевших временных файлов. Файловая операция и транзакция PostgreSQL не образуют одну атомарную транзакцию: после сбоя приложение должно уметь сопоставить файлы и записи.

### P2-01. Изменить порядок анализа, чтобы не описывать заведомо ненужные кадры

Места: PLAN.md, строки 77–82.

Сейчас массовый анализ объединяет дешёвые проверки и VLM-описание до окончательного отбора. Это может потратить большую часть времени на дубли и исключённые изображения.

Предлагаемый порядок: импорт и нормализация → технические проверки/дубли/число людей → предварительный набор и ручная проверка → геометрия подготовки → подписи → окончательная проверка → экспорт. Для рекомендации до подписей можно использовать независимые визуальные признаки. Пользователь по-прежнему может выбрать «описать всю коллекцию».

На первом этапе показывать оценку объёма работы: сколько файлов потребуют нового запроса, сколько уже имеют актуальный результат и сколько будет пропущено.

### P2-02. Количество изображений и подписи должны зависеть от цели обучения

Места: PLAN.md, строки 71, 132, 146.

Ориентир 15–40 изображений в приведённом руководстве FLUX.2 Klein раскрывается главным образом на примере стилевой LoRA. Его нельзя превращать в оптимальное число для любого персонажа. [Руководство BFL](https://huggingface.co/blog/black-forest-labs/flux-2-klein-lora).

Рекомендация должна учитывать цель (идентичность, одежда, стиль), полезные вариации, группы дублей и ручные закрепления. Показывать диапазон и недостающее покрытие; не обещать математически лучший размер набора без оценки результата обучения.

Раздел 3 предлагает общее короткое описание с внешностью и стилем, а раздел 7 — отдельные стратегии. Сделать стратегию единой настройкой профиля: какие постоянные признаки связывать с триггером, какие вариации нужно описывать. Не применять правило «всегда подробно описывать лицо и волосы» ко всем задачам и не объявлять одинаковые подписи безусловной ошибкой.

### P2-03. Уточнить возможности и проверку LM Studio

Места: PLAN.md, строки 50–65, 146.

Qwen3.5 4B как начальный кандидат и 9B для сравнения подходят как предварительная гипотеза. Каталог LM Studio подтверждает эти размеры и vision-возможности семейства, но не доказывает качество подписей на данных пользователя. [Каталог LM Studio](https://lmstudio.ai/models/qwen3.5).

GET /v1/models показывает модели, видимые серверу, и при JIT может включать скачанные, но не загруженные. Для статуса загруженных экземпляров и vision-возможностей использовать поддерживаемый установленной версией native API; текущая документация описывает loaded_instances и capabilities в GET /api/v1/models. При недоступности такого API показывать «статус неизвестен» и опираться на пробный запрос. [OpenAI-совместимый список](https://lmstudio.ai/docs/developer/openai-compat/models), [native API](https://lmstudio.ai/docs/developer/rest/list).

Хранить точную модель, квантование, prompt и параметры генерации вместе с результатом. Сравнивать 4B и 9B по времени на файл, доле выдуманных деталей и объёму ручных исправлений. Профиль RTX 4070 Ti Super 16 GB относится к подготовке данных и не означает, что обучение каждой целевой LoRA поместится на этой карте.

Если для анализа нужны машинные поля, использовать JSON Schema после проверки совместимости модели; валидность JSON не подтверждает правильность описания картинки. При неподдерживаемом режиме оставить текстовое описание и независимые CV-проверки. [Structured Output LM Studio](https://lmstudio.ai/docs/developer/openai-compat/structured-output).

### P2-04. Ограничить поток событий и определить протокол восстановления

Места: PLAN.md, строки 28–33, 93, 161–166.

Outbox уже предусмотрен правильно. Нужно различить долговременную историю решений и очередь доставки: успешные доставки и частые проценты нельзя хранить бесконечно без политики очистки. Задать срок хранения, лимиты размера очереди и диагностику недоставляемых событий.

Прогресс можно объединять по задаче и отправлять с ограниченной частотой; завершение и ошибки отправлять сразу после фиксации. Статус и счётчики в PostgreSQL сохраняются независимо от частоты событий. Избегать миллионов событий от загрузок по байтам.

Указать область версии — задача, элемент или ревизия; версии разных объектов не сравниваются между собой. При подписке и загрузке snapshot учитывать гонку: буферизовать новые события до применения snapshot и затем применять только более новые версии. Уведомления о побочных действиях также должны иметь idempotency key.

Определить JSON-схемы API/событий и версию контракта между PHP, Python и TypeScript. Внутренний endpoint не должен случайно проксироваться наружу вместе с общими маршрутами.

### P2-05. Уточнить импорт, пути и правила удаления

Места: PLAN.md, строки 45, 76, 109–110, 152–157.

При импорте папки учитывать существующие TXT-подписи, одинаковые базовые имена в разных вложенных папках, повтор передачи после обрыва и распознанные дубли. Существующие подписи должны получать источник «импорт» и защиту от случайной перегенерации.

Пользовательский Windows-путь и путь внутри контейнера различаются. Нужен список разрешённых смонтированных корней с понятными именами, отображение Windows/WSL-пути и возможность скачать ZIP. Браузер не может произвольно записывать результат в любой путь Windows; произвольная строка пути в UI эту задачу не решает.

Зафиксировать поддерживаемые форматы и правила EXIF, ICC/sRGB, прозрачности и анимации. Для прозрачного PNG перед преобразованием в RGB нужен явный фон с предпросмотром. Проверять размер декодированного изображения и запас диска до запуска партии.

Корзина должна показывать срок хранения и объём. Удаление исходника, на который ссылаются ревизии, не должно незаметно ломать историю. Кеш и временные артефакты должны иметь отдельную безопасную очистку.

### P2-06. Уточнить эксплуатацию и проверку профилей тренеров

Места: PLAN.md, строки 44–46, 140–148, 170–180, 227.

Healthcheck показывает состояние контейнера; обычная restart policy Docker срабатывает при завершении процесса, а не автоматически от самого статуса unhealthy. Нужны тайм-ауты, завершение зависшего worker под управлением его процесса, корректная остановка и восстановление соединений. Для порядка старта использовать service_healthy, не полагаясь на него как на механизм восстановления работающего приложения. [Restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/), [Compose startup order](https://docs.docker.com/compose/how-tos/startup-order/).

Резервная копия должна включать БД, библиотеку, конфигурацию и ключ шифрования Laravel, необходимый для сохранённых токенов. Указать согласованный способ получения копии и восстановления, фиксацию версий зависимостей и миграцию БД при обновлении.

Матрица архитектур — правильное решение, но реализацию не стоит блокировать полной проверкой всех тренеров. Начать с одного проверенного сочетания модель/тренер и универсального экспорта image + TXT. Остальные комбинации добавлять с явным статусом.

FLUX.3 Image Klein и обучение base-варианта подтверждаются документацией. Для Z-Image текущая документация Musubi рекомендует base для обучения; возможность применения такого адаптера к выбранному Turbo-варианту проверять отдельно. [FLUX.3](https://huggingface.co/blog/flux-3), [Musubi Z-Image](https://github.com/kohya-ss/musubi-tuner/blob/main/docs/zimage.md).

Уточнить вид задачи: обычный датасет image + caption не равен датасету для image-edit обучения. Qwen Image и Qwen Image Edit должны иметь разные профили, если последний войдёт в объём работ. [Musubi Qwen Image](https://github.com/kohya-ss/musubi-tuner/blob/main/docs/qwen_image.md).

## Что улучшить в интерфейсе

1. **Создание коллекции за один шаг.** Имя и необязательные эталоны персонажа. Тренер, buckets и пути экспорта выбирать при подготовке конкретного набора; коллекция уже задумана независимой от профиля.
2. **Постоянные вкладки внутри коллекции.** «Исходники», «Проверка», «Подготовленные наборы», «Экспорты». Сохранять фильтры, прокрутку, размер карточек и выделение отдельно для каждой.
3. **Центр задач поверх всех коллекций.** В нём видно «проверено 120/500», «готово к экспорту 68», «описания 12/68», очередь и время ожидания. Для ошибок — одна сводка с раскрытием файлов, без сотен всплывающих уведомлений.
4. **Один экран проверки.** Крупное изображение, эталон/похожие кадры, рамки детектора, причина и подпись. После решения открывать следующий спорный кадр, сохраняя возможность отменить последнее действие.
5. **Пакетные подписи с предварительным просмотром.** Поиск/замена, добавление триггера, блокировка ручных подписей, фильтры «нет подписи» и «подпись устарела после crop». Явно показывать область операции: выбранные 20 или все 500 по фильтру.
6. **Объяснимые наборы.** Сравнивать компактный и разнообразный набор по добавленным/убранным кадрам и покрытию, а не только по баллу. Закреплённые кадры видны; пользователь может указать «эти позы важны».
7. **Предпросмотр кадра для обучения.** Синхронный zoom исходника и подготовленной версии, рамка видимой области, предупреждение о потере головы/рук и отметка о необходимости пересмотреть подпись.
8. **Понятное завершение экспорта.** Число пар, версия, профиль, размер, путь, результат preflight, «Скачать ZIP» и «Редактировать как новую версию». Незавершённое сохранение подписи блокирует публикацию до сохранения или явного отменённого изменения.
9. **Проверка на реальном масштабе.** Сотни кадров в одной коллекции и несколько тысяч в библиотеке: серверная пагинация/фильтрация, готовые миниатюры, ленивое чтение оригиналов, отсутствие автоматического открытия 500 полноразмерных изображений.
10. **Разделить простые и расширенные настройки.** Пользователю нужны результаты и действия; lease, outbox и circuit breaker показываются в технической диагностике, а в обычном интерфейсе — «Ожидание модели», «Повтор через …», «Подключение восстанавливается».

## Предлагаемый порядок реализации

1. Сквозной сценарий на 20–30 изображениях: импорт → просмотр → ручная подпись/crop → сохранённый набор → один проверенный экспорт. Сразу сохранить оригиналы и заложить ревизии.
2. Фоновая обработка, аренда элементов задач, outbox, Node-события, восстановление после перезапуска и один профиль LM Studio. Здесь проверить сохранность ручных изменений.
3. Дубли, детекция людей, очередь ручной проверки, эталоны персонажа и объяснимый отбор. Сверить решения на размеченной пользователем выборке.
4. Удобные массовые операции, несколько коллекций, справедливая очередь, очистка места и резервирование.
5. Расширение проверенных профилей тренеров и продвинутых рекомендаций.

Одновременно строить все варианты тренеров, сложную кластеризацию и автоматическую оценку оптимального числа изображений для первой рабочей версии не требуется. В MVP достаточно качественного сквозного сценария, понятных решений и безопасного восстановления.

## Проверки, которые нужно заложить в приёмку

| Сценарий | Ожидаемый результат |
| --- | --- |
| Ручная правка во время генерации подписи | Поздний ответ сохранён как предложение, ручная правка остаётся. |
| Старый worker вернулся после истечения аренды | Он не может заменить опубликованный файл или результат нового worker. |
| Пропал ответ complete после записи результата | Повтор запроса не создаёт второй результат и не портит счётчики. |
| Потеря сокета, повтор/перестановка прикладных событий, гонка snapshot | UI сходится к актуальному состоянию PostgreSQL. |
| Несколько коллекций и одновременный vision-тест | Соблюдается общий лимит запросов LM Studio. |
| LM Studio выгружена, тайм-аут, сон Windows | Зависимые этапы ожидают восстановления; готовые результаты и ручная работа сохраняются. |
| Сбой записи или нехватка диска | Нет готового экспорта с неполными парами; доступен понятный повтор. |
| Изменение crop или caption после экспорта | Предыдущая ревизия воспроизводима; создаётся новая версия. |
| Два человека, отражение, крупный портрет, рисунок | Измерены ложные пропуски/исключения; сомнительные случаи направлены на проверку. |
| Импорт папок с одинаковыми именами и TXT | Нет коллизий и потери существующих подписей. |
| Выбранный профиль тренера выполняет crop | Предпросмотр согласуется с фактически используемой геометрией. |
| Восстановление из резервной копии | Доступны коллекции, файлы, ревизии и зашифрованные настройки. |

Пороговые значения качества детектора и скорости интерфейса нужно зафиксировать после пробной выборки и измерений на целевом компьютере. Из текущего плана нельзя вывести достоверный ETA для 500 изображений или гарантировать качество обученной LoRA.
